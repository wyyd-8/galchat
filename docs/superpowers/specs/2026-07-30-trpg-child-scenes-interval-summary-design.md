# TRPG 子场景、等待状态与区间摘要设计

`coc_module_location` 只保存可选择大场景。子场景由 KP 自由命名，使用 `trpg_runtime_child_scene` 保存运行时名称；子 Plan 继承所属大场景的 `context_id`，以 `plan_id` 区分运行实例。

## 1. 文档目的

本文档定义 GalChat TRPG 跑团中父子场景的运行语义、KP 工具、调查员等待状态、模组上下文边界，以及基于消息序号区间的场景摘要替换算法。

设计目标是支持调查员分头行动时由 KP 依次主持各队剧情，同时把已经结束的连续探索过程替换为摘要，控制长期上下文长度。

本文档只定义设计，不包含实现代码。

## 2. 核心结论

子场景是运行时行动分隔，不是模组知识加载边界。

- 当前主场景及其全部子项的模组内容始终一起提供给 KP。
- 打开子场景不会加载任何额外模组信息。
- 子场景自身的模组上下文为空，只保存运行所需的地点引用、父计划、参与者、状态和消息序号边界。
- 子场景主要用于调查员分头行动。全员共同移动时应继续停留在主场景中。
- 服务端允许 KP 把全部调查员加入子场景，但提示词明确说明这种做法不推荐。
- KP 不能交替推进多个开启场景。运行时始终只有栈顶场景能够产生剧情消息。
- 场景摘要通过全局消息序号区间替换原文。父场景摘要覆盖其所有子场景摘要，最终上下文只使用没有被更长摘要包含的极大区间。

## 3. 术语

### 3.1 模组地点

模组作者提供的地点结构，例如：

`coc_module_location` 不保存父子关系。每条地点都是可选择的大场景，地点内容是静态模组知识。

### 3.2 主场景

玩家从全局选景阶段进入的探索场景。主场景绑定一个模组地点，并加载该地点的完整内容。

### 3.3 子场景

KP 在主场景或另一子场景内，为分头行动的一组调查员创建的临时运行分支。

子场景由 KP 根据当前剧情自由命名，不引用静态模组地点，也不加载额外模组内容。它只负责：

- 限定接下来参与行动轮的调查员；
- 形成严格的场景栈；
- 产生连续的消息序号区间；
- 在关闭时生成能够替换该区间原文的摘要。

### 3.4 当前场景

场景栈顶部、当前允许产生剧情消息的场景。

运行时向 KP 显示完整路径，例如：

```text
森林 - 临时藏身处 - 地下通道
```

### 3.5 等待调查员

结束子场景并返回父场景后，暂时不参加父场景行动轮的调查员。

等待不是信息权限，也不是角色离开会话。所有 Agent 仍然能够读取相同的公开探索记录。等待只影响行动轮调度。

## 4. 设计原则

### 4.1 子场景只处理行动分隔

KP 仅应在以下情形使用子场景：

1. 调查员决定分头行动；
2. 一队调查员进入需要独立推进行动轮的地点或区域；
3. KP 需要先完整处理该队剧情，再返回父场景处理其他调查员。

以下情形不应使用子场景：

- 所有调查员共同移动到同一个地点；
- KP 只是希望查询模组资料；
- 只需要一句简短叙事便能完成的临时移动。

全员进入子场景不属于服务端错误。工具调用仍然允许成功，但系统提示应明确说明：如果调查员没有分头行动，应始终保持在主场景中。

### 4.2 公开信息不按调查员过滤

所有 Agent 都能看到公开剧情和摘要。系统不根据子场景参与者限制消息可见性。

如果某项信息在角色叙事上尚未共享，由 KP 明确提醒“你的调查员还不知道这件事”。系统不据此裁剪上下文。

### 4.3 父场景在子场景期间暂停

KP 不能交替推进父场景和子场景，也不能交替推进两个兄弟子场景。

打开子场景后：

- 父场景保留但暂停；
- 只有栈顶子场景能够产生剧情消息；
- 子场景关闭并出栈后，父场景才恢复。

这保证场景对应的消息序号区间只有包含或分离关系，不会部分相交。

## 5. 模组上下文

### 5.1 加载当前大场景

进入主场景时，服务端组装当前大场景的名称和完整内容。

示例：

```xml
<module-scene-context>
  <main-scene path="森林">
    主场景完整模组内容
  </main-scene>
</module-scene-context>
```

主场景及任意深度子场景获得完全相同的 `<module-scene-context>`。

### 5.2 子场景不追加地点内容

子场景计划继承大场景的 `context_id`，并由 `trpg_runtime_child_scene` 以 `plan_id` 保存运行时名称。子场景没有独立模组文本上下文，始终复用所属大场景的内容。

## 6. KP 运行时上下文

每次调用 KP 时，服务端都追加当前场景和参与者上下文。

普通行动轮示例：

```xml
<current-scene-runtime>
当前场景：摩根老大的住宅 - 书房

本轮参与行动的调查员：
- 艾琳
- 威廉
- 亨利
</current-scene-runtime>
```

要求：

- 当前场景使用从主地点开始的完整路径；
- 名单包含本轮能够产生行动步骤的全部调查员；
- KP 不出现在调查员名单中；
- 使用人物卡名称，不向模型暴露内部 ID；
- 名单顺序与行动计划顺序一致。

### 6.1 子场景引入轮

子场景进入后的第一轮只有 KP 引入，不安排调查员行动。

该轮上下文仍列出即将在子场景中行动的调查员：

```xml
<current-scene-runtime>
当前场景：摩根老大的住宅 - 书房

当前为场景引入轮。
引入完成后参与行动的调查员：
- 艾琳
- 威廉
</current-scene-runtime>
```

KP 使用已经存在的统一模组场景上下文，描述这组调查员进入子地点后最初能够观察到的信息。

### 6.2 存在等待调查员

等待调查员不进入“本轮参与行动”名单，并追加等待说明：

```xml
<current-scene-runtime>
当前场景：摩根老大的住宅

本轮参与行动的调查员：
- 亨利

等待中的调查员：
- 艾琳
- 威廉

等待中的调查员此前已经在子场景中独立行动了一段时间。
请根据当前剧情、时间经过、位置关系和队伍行动，
选择自然且合适的汇合时机调用 resumeWaitingInvestigators。
工具生效后，他们将从下一轮开始恢复行动。
</current-scene-runtime>
```

没有等待调查员时，不显示等待段落，也不向 KP 提及恢复工具。

## 7. KP 工具

### 7.1 `startChildScene`

建议签名：

```text
startChildScene(
  childSceneName: String,
  investigatorNames: List<String>
)
```

工具描述：

```text
当调查员决定分头行动，并且其中一队进入需要独立推进的
地点或行动区域时，创建动态子场景。
子场景仅分隔行动轮，不会提供更多模组信息。
它继承当前大场景的模组上下文。
如果所有调查员一起行动，应继续停留在主场景中，
不推荐调用本工具。
```

开放条件：

- 当前处于场景探索阶段；
- 当前步骤由 KP 执行；
- 当前没有待完成的检定、战斗或场景切换；
- 当前至少有一名可选择的活动调查员。

服务端校验：

- `childSceneName` 非空且不超过 200 个字符；
- `investigatorNames` 非空、无重复且均能准确匹配；
- 被选择者都是当前场景中的活动调查员；
- 调用者是当前 KP；
- 同一回复步骤没有已经成功提交的子场景创建命令。

服务端允许选择全部活动调查员，不因未形成实际分队而拒绝。是否合理使用由 KP 提示词约束。

工具成功只返回：

```text
已创建子场景“阁楼”，调查员艾琳、威廉将进入该场景。
```

工具不直接生成场景介绍，也不要求模型在当前回复中提前描述子场景内部信息。

调用后，当前 KP 公开回复仍属于父场景。KP 需要在原有叙事或裁定基础上明确说明谁去了哪里，例如：

> 艾琳和威廉沿着楼梯前往阁楼，其他人继续留在教堂大厅。

该回复成功提交后才正式激活子场景。

### 7.2 `resumeWaitingInvestigators`

建议签名：

```text
resumeWaitingInvestigators(
  investigatorNames: List<String>
)
```

工具描述：

```text
等待中的调查员此前已经在子场景中独立行动了一段时间。
请根据当前剧情、时间经过、位置关系和队伍行动，
选择一个自然且合适的汇合时机调用本工具，
使指定调查员从下一轮开始重新参与行动。
不要仅因为工具可用就立即调用。
```

该工具仅在当前场景存在至少一名等待调查员时提供。

服务端校验：

- 当前处于场景探索阶段；
- 调用者是当前 KP；
- 名单非空、无重复且准确匹配；
- 名单中的调查员当前都处于 `WAITING`；
- 不修改已经创建的当前行动轮。

成功结果：

```text
艾琳、威廉已结束等待，将从下一轮开始正常参与行动。
```

KP 可以一次恢复一人、多人或全部等待调查员。

### 7.3 `finishSceneExploration`

复用现有 KP 场景结束工具。

关闭子场景时：

1. 当前 KP 回复完整提交；
2. 确定子场景消息序号终点；
3. 生成子场景摘要，失败时保留原文；
4. 子场景出栈；
5. 恢复父场景；
6. 子场景参与者在父场景中变为 `WAITING`；
7. 父场景原有其他活动调查员保持 `ACTIVE`。

关闭主场景时，按照既有主场景结算流程处理。

## 8. 调查员参与状态

场景计划中的调查员至少包含：

```text
ACTIVE
WAITING
```

### 8.1 `ACTIVE`

- 进入普通行动轮；
- 可以被 `startChildScene` 选择；
- 出现在 KP 的本轮参与调查员名单中。

### 8.2 `WAITING`

- 不进入普通行动轮；
- 不出现在本轮参与调查员名单中；
- 出现在等待调查员名单中；
- 可以被 `resumeWaitingInvestigators` 恢复；
- 仍属于当前场景参与者；
- 不影响公开消息和摘要可见性。

### 8.3 子场景关闭

设父场景原有活动调查员为 A、B、C，KP 将 A、B 加入子场景：

```text
子场景关闭前：
子场景：A=ACTIVE，B=ACTIVE
父场景暂停：A=ACTIVE，B=ACTIVE，C=ACTIVE

子场景关闭并返回父场景后：
父场景：A=WAITING，B=WAITING，C=ACTIVE
```

父场景恢复后的下一轮只安排 C 和 KP。KP 可以选择合适时机恢复 A、B。

### 8.4 场景关闭时仍在等待

KP 不需要在关闭场景前恢复全部等待调查员。

- 如果关闭主场景，等待者视为最终与其他调查员一起离开；
- 如果关闭的场景仍有父场景，该场景的全部调查员，无论 `ACTIVE` 或 `WAITING`，都随场景一起返回父场景，并在父场景中进入 `WAITING`。

这使嵌套场景保持一致。

## 9. 子场景生命周期

### 9.1 创建

```text
父场景 KP 调用 startChildScene
→ 记录待提交的场景创建命令
→ 工具返回确认文本
→ KP 在父场景公开说明谁去了哪里
→ KP 回复完整成功
→ 创建子场景计划
→ 子场景压栈并成为活动计划
```

场景创建命令应与当前回复步骤绑定。工具调用成功但后续模型输出或持久化失败时，不得留下已经激活的半完成子场景。

### 9.2 引入

```text
子场景成为活动计划
→ 创建仅包含 KP 的 INTRO 轮
→ KP 读取统一模组场景上下文
→ KP 生成子场景初始可观察信息
→ INTRO 成功
→ 子场景进入普通行动阶段
```

### 9.3 普通探索

子场景流程与主场景普通探索一致，包括：

- 调查员行动；
- KP 裁定；
- 检定和工具；
- 战斗；
- 调查员结束探索；
- KP 结束场景。

差异仅在于子场景关闭后返回父场景。

### 9.4 关闭与返回

```text
子场景请求结束
→ 完成当前回复和待处理流程
→ 确定 [startSequence, endSequence]
→ 使用已经压缩的区间内容生成摘要
→ 子场景出栈
→ 父场景恢复
→ 子场景调查员在父场景中进入 WAITING
```

### 9.5 严格栈约束

场景关闭必须后进先出。父场景存在未关闭子场景时不能直接完成最终摘要。

若需要强制结束父场景，应先从最深层开始依次关闭和总结子场景，再生成父摘要。

## 10. 摘要区间模型

### 10.1 全局消息数轴

同一会话的公开完成消息通过 `sequence_no` 形成：

```text
[1, currentSequence]
```

每份有效摘要声明自己完整覆盖：

```text
[startSequence, endSequence]
```

摘要只替换模型 Prompt 中的原文，不删除持久化消息。

### 10.2 层流区间

由于 KP 只能推进栈顶场景，场景摘要区间只允许：

- 分离；
- 相邻；
- 完整包含；
- 完全相同。

禁止部分相交。

合法：

```text
[10,20] [30,40]
[10,40] [15,20]
[10,20] [10,20]
```

非法：

```text
[10,25] [20,40]
```

### 10.3 子摘要与父摘要

示例：

```text
教堂       [1,100]
├── 阁楼   [20,40]
│   └──夹层[25,32]
└── 地下室 [60,80]
```

夹层关闭后：

```text
原文[1,24] + 夹层摘要[25,32] + 原文[33,current]
```

阁楼摘要的生成输入：

```text
阁楼原文[20,24]
+ 夹层摘要[25,32]
+ 阁楼原文[33,40]
```

阁楼摘要 `[20,40]` 生成后，在普通上下文中替换夹层摘要。

教堂摘要的生成输入：

```text
教堂未覆盖原文
+ 阁楼摘要[20,40]
+ 地下室摘要[60,80]
```

教堂摘要 `[1,100]` 生成后，在普通上下文中替换所有内部子摘要。

父场景摘要不得重新读取已经被有效子摘要覆盖的子场景原文。

## 11. 最大区间摘要选择

### 11.1 选择规则

装配探索记录上下文时：

1. 查询当前会话中所有已完成且 `endSequence <= currentSequence` 的有效摘要；
2. 相同 `[startSequence,endSequence]` 只保留最高版本，版本相同则保留最新记录；
3. 按 `startSequence ASC, endSequence DESC` 排序；
4. 如果当前摘要包含已经选中的较短摘要，用当前摘要替换较短摘要；
5. 如果当前摘要被已经选中的较长摘要包含，丢弃当前摘要；
6. 最终只保留没有被其他摘要包含的极大区间。

### 11.2 上下文输出

从 sequence 1 扫描到 `currentSequence`：

1. 输出下一个摘要区间之前的未覆盖原文；
2. 输出摘要；
3. 将游标移动到 `endSequence + 1`；
4. 重复直到没有摘要；
5. 输出最后一个摘要之后的未覆盖原文。

最终结果是：

```text
未覆盖原文 + 极大摘要 + 未覆盖原文 + 极大摘要 + ...
```

上下文装配不需要读取或理解场景树。场景树只负责产生合法区间，sequence 区间负责最终压缩。

## 12. 区间起止点

每条消息归属消息创建时位于栈顶的场景。

- 调用 `startChildScene` 的当前 KP 回复属于父场景；
- 该回复完整成功后子场景入栈；
- 子场景入栈后第一条已完成公开消息是子场景 `startSequence`；
- 调用场景结束工具后的最后一条公开回复属于当前子场景；
- 该回复完整提交后确定 `endSequence` 并出栈；
- 后续消息重新属于父场景。

如果一个场景没有产生任何公开完成消息，则不生成摘要区间。

父场景的区间从其第一条公开完成消息开始，到其关闭前最后一条公开完成消息结束，连续包含所有子场景区间。

## 13. 摘要内容要求

摘要至少保留：

- 场景目标和最终结果；
- 参与调查员；
- 已发生的重要行动；
- 公开发现和已经展示的材料；
- 获得或失去的重要物品；
- 关键人物状态变化；
- 对父场景产生的直接影响；
- 尚未解决的问题。

摘要只能记录已经确认的事实：

- 不加入模组隐藏真相；
- 不把调查员推测写成事实；
- 不输出模型分析过程；
- 不重复结构化状态的完整快照；
- 不承担角色级信息权限控制。

生成父摘要时，输入中的子摘要应带有原始区间和场景路径，帮助模型理解发生顺序并去重。

## 14. 摘要失败与区间异常

### 14.1 摘要失败

原始消息始终保留。摘要生成失败、返回空内容或无法验证时：

- 不写入有效覆盖区间；
- 上下文继续使用该区间原文；
- 场景可以关闭并恢复父场景；
- 后续可以重试生成摘要。

不使用“本场景探索已结束”之类无信息量文本替换完整原文。

如果更大的父摘要已经成功生成，迟到的子摘要即使生成，也会因被父摘要包含而不进入普通上下文。

### 14.2 部分相交

写入摘要前检查现有有效摘要区间。

发现部分相交时：

- 拒绝把异常摘要加入有效覆盖集合；
- 保留对应原始消息；
- 记录场景、计划和区间信息供排查；
- 不猜测应该选择哪个摘要。

### 14.3 相同区间多版本

重新生成或人工修订摘要时，可以写入相同区间的新版本。

上下文装配只使用最高版本；版本相同则使用最新记录。旧版本继续保留用于追溯。

## 16. 组件边界

### 16.1 场景栈服务

负责：

- 创建子场景计划；
- 提交延迟场景切换；
- 维护父计划引用；
- 创建 KP 引入轮；
- 关闭并弹出子场景；
- 将调查员迁移为父场景等待状态。

### 16.2 场景参与状态服务

负责：

- 查询当前场景活动和等待调查员；
- 校验工具人物名单；
- 恢复等待调查员；
- 为下一轮过滤行动参与者；
- 处理嵌套场景关闭时的等待状态传播。

### 16.3 KP 运行上下文组装器

负责：

- 解析当前场景完整路径；
- 列出本轮参与调查员；
- 识别 KP 引入轮；
- 在存在等待调查员时输出等待名单和汇合提示。

### 16.4 模组场景上下文组装器

负责：

- 从根计划引用的模组地点加载大场景内容；
- 对主场景和所有子场景返回同一份上下文；
- 不为动态子场景追加静态地点内容。

### 16.5 摘要区间选择器

负责：

- 版本归并；
- 验证区间层流不变量；
- 选择极大摘要区间；
- 生成“摘要与原文间隙”的有序上下文片段。

该组件不读取模组地点和场景父子关系。

### 16.6 场景摘要服务

负责：

- 根据场景计划序号边界请求压缩后的探索记录；
- 生成摘要；
- 校验摘要非空；
- 写入摘要区间和版本；
- 摘要失败时保留原文。

## 17. 动态工具注册

KP 场景阶段的工具集合根据运行状态动态决定：

```text
当前场景存在 ACTIVE 调查员
→ 提供 startChildScene

当前场景存在 WAITING 调查员
→ 提供 resumeWaitingInvestigators

当前处于普通场景阶段
→ 提供 finishSceneExploration
```

工具是否展示只是模型能力边界，服务端仍需在每次调用时重新校验实际状态。

同一次模型工具循环中，状态可能已经被前一次调用改变。重复或过期调用必须安全失败，不能创建重复场景或重复恢复调查员。

## 18. 保存、恢复与失败一致性

父计划、子计划、参与状态、场景阶段、序号边界和摘要记录必须进入世界存档快照。

需要保证：

- 恢复存档后场景栈顺序一致；
- 活动计划仍指向栈顶场景；
- 等待调查员状态不丢失；
- `INTRO_PENDING` 场景能够重新执行 KP 引入；
- 已完成摘要的版本和区间保持不变；
- 未完成的场景创建或恢复命令能够回滚或安全重试。

场景创建和恢复等待状态应在会话锁内完成，并使用回复步骤或工具调用记录实现幂等。

## 19. 测试要求

### 19.1 子场景工具

- KP 可以选择一名、多名或全部活动调查员；
- 全员进入允许成功，但提示词明确不推荐；
- 非 KP 调用被拒绝；
- 空名单、重复姓名、未知姓名和非活动调查员被拒绝；
- 空名称和超过长度限制的名称被拒绝；
- 当前 KP 回复失败时不激活子场景；
- 成功结果只包含创建确认，不包含场景介绍；
- 当前 KP 回复仍保存到父场景；
- 子场景第一轮只有 KP 引入。

### 19.2 模组与运行上下文

- 主场景与任意深度子场景收到相同的大场景模组内容；
- 子场景不追加静态地点内容；
- 当前场景路径正确；
- KP 上下文列出全部本轮行动调查员；
- 引入轮列出引入后参与行动的调查员；
- 等待名单只在存在等待者时出现。

### 19.3 等待与恢复

- 子场景关闭后，参与者在父场景中变为 `WAITING`；
- 父场景原有其他调查员保持 `ACTIVE`；
- 等待者不进入下一轮行动计划；
- 仅存在等待者时注册恢复工具；
- 可以恢复部分或全部等待者；
- 恢复只从下一轮生效；
- 未恢复者在主场景关闭时随队离开；
- 嵌套子场景关闭时状态逐层传播；
- 重复恢复和过期工具调用安全失败。

### 19.4 区间摘要

- 分离摘要同时替换各自原文；
- 父摘要替换所有被包含的子摘要；
- 子摘要在父摘要存在时被丢弃；
- 相同区间选择最高版本；
- 相邻区间同时保留；
- 原文间隙按顺序插入；
- 部分相交摘要被判定无效；
- 摘要失败时继续加载原文；
- 父摘要生成输入使用子摘要而不是子场景原文；
- 最终上下文顺序与原始 sequence 顺序一致。

### 19.5 保存与恢复

- 存档恢复后父子场景栈一致；
- 等待状态一致；
- 引入阶段一致；
- 摘要版本和有效区间一致；
- 未完成工具命令可安全恢复。

## 20. 第一阶段不实现

- 按调查员过滤公开上下文；
- 多个场景并行或交替推进；
- 部分相交摘要的自动修复；
- 子场景独立模组知识检索；
- 为共同移动自动切换子场景；
- 摘要之上的章节级二次压缩；
- 根据等待轮数自动恢复调查员；
- 自动判断角色是否已经通过对话共享信息。

这些能力不属于当前父子场景和区间摘要设计。
