# TRPG Agent 场景与记忆设计

## 1. 文档目的

本文档描述 GalChat 跑团功能第一阶段的核心设计，用于指导后续 AI 或开发者继续分析、拆分和实现。

本文档只定义产品语义、职责边界、上下文范围和运行流程，不规定具体类、接口、数据库表、框架用法或算法实现。后续开发应优先保持本文档中的边界，避免在没有实际需求前引入更复杂的多 Agent、分层记忆或工作流抽象。

## 2. 功能范围

第一阶段只考虑以下参与者：

- 用户：控制自己的玩家角色并参与场景。
- 玩家 Agent：控制用户选择的同行角色，与用户共同探索。
- KP Agent：负责提供场景信息、控制环境与 NPC、判断行动是否需要检定，并描述行动结果。

场景分为叙事探索、标准探索和战斗。标准探索与战斗拥有独立过程，但叙事场景只接收它们的最终结果，不接收内部逐步过程。

## 3. 核心设计原则

### 3.1 场景是上下文和记忆的基本边界

所有交互聊天、角色行动、KP 反馈、检定结果和重要事件都属于一个明确场景。

当前场景保留完整的语义上下文；场景结束后生成概要。进入新场景时，使用历史场景概要和新场景内的完整上下文，不直接携带历史场景的全部原始记录。

这里的“完整语义上下文”不包括模型的原始思维链，也不包括对后续决策没有意义的大段工具原始输出。

### 3.2 状态事实与自然语言记忆分离

角色状态、物品、伤害、线索是否获得等确定事实，不能只存在于聊天或概要中。

场景记录用于描述发生过程，场景概要用于帮助理解历史，二者都不能代替真实状态。摘要内容与真实状态冲突时，以真实状态为准。

### 3.3 KP 决定结果，玩家 Agent 只决定尝试

玩家 Agent 可以决定角色想做什么，但不能决定行动是否成功，不能自行生成骰点，也不能自行修改检定相关状态。

是否需要检定、使用什么检定以及检定后的结果，都由 KP Agent 负责。

## 4. 两种目标

### 4.1 KP 整体目标

每个场景开始时，KP Agent 必须给出一个清晰的整体目标，说明当前场景为什么存在、参与者需要解决什么问题。

整体目标应当：

- 对玩家和玩家 Agent 可理解。
- 描述需要解决的问题，不提前泄露答案。
- 在场景期间保持稳定。
- 只有场景发生根本性转变时才允许调整。

示例：调查废弃病院，寻找失踪记者留下的线索。

### 4.2 玩家 Agent 探索目标

玩家 Agent 在场景中维护一个当前探索目标，表示它现在希望从当前场景中查明、找到或取得什么。

探索目标可以是：

- 获取某项信息。
- 寻找人物或地点。
- 取得某件物品。
- 确认某个推测。
- 找到继续前进或安全离开的方式。

探索目标可以根据 KP 新提供的信息动态改变。改变时必须能用简短、明确的理由说明新信息如何影响了原目标。

探索目标服务于 KP 整体目标，但不要求每一步都直接完成整体目标。

示例：确认记者是否进入过地下室。

## 5. 玩家 Agent 的两个独立行为

玩家 Agent 的每一轮由“决策”和“行动”两个独立行为组成。二者不能合并为同一次模型行为。

### 5.1 决策行为：观察与思考合并

观察与思考属于同一个决策行为。它们的本质都是玩家 Agent 根据 KP 提供的新信息，结合历史和角色状态，调整自己的探索方向与下一步行为。

决策行为拥有完整上下文，包括：

- 角色身份、性格和当前状态。
- KP 给出的整体目标。
- 玩家 Agent 当前探索目标。
- 已结束场景的概要。
- 当前场景的完整语义上下文。
- KP 最新提供的信息和行动结果。
- 当前剩余回合等必要限制。

决策行为可以使用与记忆查询、角色状态查询、探索目标调整和场景暂停有关的工具，但不能使用检定工具。

决策行为应形成一份简短、可进入后续上下文的决策说明。它只需要表达：

- 当前哪些信息值得关注。
- 这些信息如何影响当前探索目标。
- 是否需要调整探索目标。
- 下一步准备尝试什么。

这份决策说明是外显、精简的行为依据，不是模型的隐藏思维链，不应包含冗长推演、候选答案穷举或内部提示词内容。

### 5.2 行动行为

行动行为负责把上一阶段确定的行动意图转化为符合角色身份的实际表达，包括角色说的话、动作和尝试。

行动行为只接收：

- 角色身份和表达要求。
- 当前场景上下文。
- 当前探索目标。
- 本轮决策说明和行动意图。

行动行为不读取历史场景概要，不调用任何工具，也不重新规划目标。

行动只能描述角色尝试做什么，不能宣布未知事实、检定成功、伤害结果、场景变化或其他应由 KP 决定的结果。

## 6. KP Agent 的职责

KP Agent 负责：

- 在场景开始时建立整体目标和初始情况。
- 根据用户及玩家 Agent 的行动提供新的可观察信息。
- 判断行动是否可以直接产生结果。
- 判断行动是否需要检定，并在需要时调用检定能力。
- 根据检定结果描述成功、失败、代价和场景变化。
- 维护场景事实的一致性。
- 在场景结束时提供足以生成概要的最终状态。

KP Agent 不替用户或玩家 Agent 决定行动，也不把秘密信息提前写进玩家 Agent 可见上下文。

## 7. 单轮场景流程

每轮遵循以下顺序：

1. KP Agent 给出当前可观察信息，或上一行动的最终结果。
2. 玩家 Agent 执行决策行为，结合观察完成简要思考，并确认或调整探索目标。
3. 如果玩家 Agent 决定继续，则执行行动行为。
4. KP Agent 接收行动，判断是否需要检定。
5. 如需检定，由 KP Agent 发起并获得检定结果。
6. KP Agent 根据行动与检定结果生成新的场景反馈。
7. 本轮的决策、行动、结果和重要状态变化归入当前场景上下文。
8. 进入下一轮，或进入场景暂停流程。

用户角色的行动同样由 KP Agent 裁定，但不要求经过玩家 Agent 的决策和行动阶段。

## 8. 场景记忆

### 8.1 当前场景记忆

当前场景保留：

- KP 整体目标。
- 玩家 Agent 当前探索目标。
- 用户与角色的聊天内容。
- 玩家 Agent 的简要决策说明。
- 用户和玩家 Agent 的行动。
- KP 给出的结果。
- 检定结果。
- 标准探索或战斗的最终结果。
- 对后续场景有意义的事件和状态变化。

### 8.2 历史场景概要

场景结束后生成简洁概要，至少说明：

- 场景整体目标。
- 最终结果。
- 获得的重要信息或物品。
- 发生的重要事件。
- 关键状态变化。
- 尚未解决的问题。
- 下一场景可能承接的位置。

新场景加载每个历史场景的概要，但不加载这些场景的完整对话与行动过程。

概要只记录已经确认的事实。玩家 Agent 的判断、怀疑或探索目标不能在未被 KP 确认时写成事实。

## 9. 标准探索与战斗

标准探索和战斗与普通叙事过程分离。

它们可以拥有自己的内部流程，但完成后只向所属场景提供对叙事有意义的最终结果，例如：

- 胜负或探索结论。
- 角色状态变化。
- 消耗或获得的资源。
- 发现的重要信息。
- 对人物关系或后续场景产生影响的事件。

内部逐次检定、回合细节和中间计算不进入普通场景上下文。

## 10. 场景暂停与最大轮数

场景暂停由玩家 Agent 在决策阶段通过专用工具提出。

玩家 Agent 可以在以下情况下暂停场景：

- KP 整体目标已经完成。
- 当前场景的重要信息已经获得。
- 后续推进需要进入新的场景。
- 当前场景已经无法继续提供有效信息。
- 角色决定撤离或暂时停止探索。

提出暂停后，不再开始新的普通行动。尚未完成的既有行动或检定应先得到最终结果，然后结束场景并生成概要。

场景拥有最大轮数限制。达到最大轮数后，即使玩家 Agent 没有主动暂停，也必须结束当前场景并生成概要，防止循环无限延长。

## 11. 上下文边界

不同阶段使用不同上下文：

| 阶段 | 历史场景概要 | 当前场景 | 工具权限 |
| --- | --- | --- | --- |
| 玩家 Agent 决策 | 使用 | 完整使用 | 允许非检定工具 |
| 玩家 Agent 行动 | 不使用 | 使用 | 不允许 |
| KP Agent 裁定 | 按需要使用 | 完整使用 | 允许检定及 KP 工具 |

玩家 Agent 的决策阶段可以理解历史并调整方向；行动阶段只负责落实已经形成的决定；KP Agent 负责将行动转化为可靠的场景结果。

## 12. 必须保持的不变量

后续设计与开发必须保持以下约束：

1. 每个场景都有 KP 给出的明确整体目标。
2. 玩家 Agent 同一时间只维护一个当前探索目标。
3. 观察与思考属于同一个决策行为。
4. 决策与行动是两次独立行为。
5. 只有决策行为拥有完整历史上下文和玩家侧工具权限。
6. 行动行为不调用工具，也不决定行动结果。
7. 玩家 Agent 不调用检定能力，所有检定由 KP Agent 发起。
8. 当前场景保留完整语义上下文，历史场景只进入概要。
9. 战斗与标准探索只向普通场景返回最终结果。
10. 玩家 Agent 可以主动暂停场景，最大轮数提供强制终止兜底。
11. 场景概要不能把角色推测写成已经确认的事实。
12. 不保存或要求模型输出原始思维链。

## 13. 第一阶段暂不设计的内容

第一阶段不主动引入：

- 多级或章节级摘要。
- 复杂的目标树和任务规划器。
- 独立 NPC Agent。
- 多玩家 Agent 并行协商。
- 自动反思或自我批评循环。
- 复杂的长期记忆评分和淘汰机制。
- 对所有工具过程进行长期上下文保留。

这些能力只有在基础场景循环验证后出现明确需求时再设计。
